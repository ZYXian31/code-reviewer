# 面向特定场景的代码评审工具研发 —— AI 提效实践报告

**AI 提效实践记录**

---

## 一、任务概述

本作业要求研发一套"面向特定场景的代码评审工具"：以一段代码或一个代码文件为输入，自动执行静态检查，识别语法严重错误、规范问题和场景化规则违规，并输出结构化评审报告，形成完整链路：

> 代码导入 → 语法解析（AST） → 规则检查 → 问题定位与分级 → 结构化报告输出

工具需要覆盖三类核心检查能力（语法严重错误 / 变量声明未使用 / 特定场景规则），并满足工程要求：基于 AST 而非字符串匹配、规则配置化管理、异常处理与日志、至少一种结构化输出、支持按场景加载规则集。

本报告同时记录使用 AI 编程工具（Claude Code）完成需求分析、架构设计、编码、调试、测试与文档的全过程，作为"AI 工具运用"维度的过程证据。

## 二、工具总体架构和技术选型

### 2.1 架构总览

```
┌──────────────────────────────────────────────────────────────────────┐
│                         code_reviewer（Python 3.9+）                  │
│                                                                      │
│  CLI (cli.py) ──► ReviewEngine (engine.py) ──► rules/* (规则注册表)    │
│   │单文件/目录/stdin       │ 读取源码 → ast.parse                    │
│   │--scenario/-o/-f/--upload│  ├── 成功: AST 规则 + 场景规则           │
│   │--list-rules/--strict    │  └── 失败: 恢复路径规则                  │
│   │                                                                  │
│   │  Issue 模型 (models.py)    配置层 (config.py)                     │
│   │  行/列/级别/规则/描述/建议    rules.json + scenarios/*.json        │
│   │                                                                  │
│   └─ formatters.py（JSON / Markdown / HTML） + uploader.py（云文档）   │
│             │                                    │                   │
│         reports/  ← 报告保存                i 讯飞云文档（可选上传）    │
└────────────┴─────────────────────────────────────────────────────────┘
```

采用**分层 + 注册表**架构：`引擎引擎层`只负责编排（解析→选规则→执行→去重→分级→汇总），`规则层`每条规则独立成类、通过 `@register` 装饰器注册，`配置层`用 JSON 控制启停与分级。新增一条规则 = 新增一个类 + 在 `rules.json` 加一行配置，**零改动核心代码**；新增一个场景 = 在 `config/scenarios/` 下新增一个 JSON 文件。

### 2.2 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.9+，纯标准库 | 零第三方依赖，评审工具本身即检查"依赖健康"；便于在 CI 上一键部署 |
| 静态分析 | `ast` 模块（核心）+ `tokenize`（恢复路径） | 作业明确要求基于 AST；`ast` 是 CPython 官方解析器，覆盖全部语法特性 |
| 配置 | JSON（`rules.json` / `scenarios/*.json`） | 作业指定 JSON/YAML；JSON 无依赖、可注释说明、易合并 |
| 报告 | JSON（机器可读）+ Markdown（文档可贴）+ HTML（可视化自查） | 覆盖"可查看、可保存、可程序化对比"三类需求 |
| 日志 | `logging` + `RotatingFileHandler` | 滚动日志文件，生产可审计 |
| 上传 | `urllib` webhook + Lark Cli(i讯飞版) 两种模式 | 对接团队云文档，认证为内网配置 |

### 2.3 关键设计：AST 失败恢复路径

测试集里 `if user_id = 100:`（test_case_03）和 f-string 缺少闭合 `}`（test_case_08）都是**真实语法错误，`ast.parse` 直接失败**。若只依赖 AST，这两条 error 级问题必然漏报（作业红线）。因此引擎设计了恢复路径：

1. **assign-in-condition**：用 `tokenize`（词法层能正常出 token）扫描 `if/elif/while` 条件中的裸 `=` token（区分 `==`/`:=`/`<=` 等单 token 运算符与括号内关键字参数）；
2. **unbalanced-bracket**：字符级扫描器，正确处理单/双/三引号、转义、注释、f-string 前缀（`f`/`rf`/`F`）与内部花括号配对；
3. **syntax-error 兜底**：以上两者都未命中才报告通用语法错误，且命中具体缺陷时**抑制**兜底规则，避免同一文件重复报错（影响漏报/误报统计）。

该设计使三类 error 级规则（assign-in-condition / unbalanced-bracket / syntax-error）在"AST 不可用"时仍能精确定位问题行号与列号。

### 2.4 关键设计：作用域分析（unused-variable / undefined-variable）

参照 pyflakes 语义实现手写作用域分析（模块/函数/类/lambda/推导式五类作用域）：

- 收集**绑定**（赋值、解包、for 目标、海象、函数/类定义、with/except-as、导入、参数）与**使用**（Load 上下文），之后做**名字解析**（当前作用域→外层→模块→builtins）；
- 误报控制：模块级变量视为公开 API 不报；参数、with-as、except-as、下划线开头变量不报；增强赋值视为读+写；注解中的引用算"使用"（否则 `from typing import List` 只用于注解会被误报）；try 块内的容错导入（`try: import ujson as json / except: import json`）不报 unused-import；
- 与 Python 运行时一致：函数体解析**跳过类作用域**（方法内裸引用类属性运行时会 NameError）。

### 2.5 关键设计：场景规则集（配置驱动）

`config/scenarios/grading.json` 定义批改场景的专属规则：

```json
{
  "name": "grading",
  "description": "批改/评分场景：评分相关函数必须以 score_ 或 grade_ 开头",
  "rules": [
    {
      "rule": "scenario-rule",
      "params": {
        "required_prefixes": ["score_", "grade_"],
        "keywords": ["answer", "reference", "score", "grade", "批改", "评分", ...],
        "message": "批改场景下，评分相关函数应以 {prefixes} 开头",
        "severity": "warning"
      }
    }
  ]
}
```

引擎在通用（general）场景只跑基线 8 条规则；指定 `-s grading` 时**叠加**场景规则。关键词匹配函数名/docstring/参数名，前缀判定支持多个前缀。新增场景（如"评测引擎"）只需新增 JSON 文件。

## 三、规则定义与 AST 检查逻辑

| 规则 | 类别 | 级别 | AST/静态逻辑 | 触发条件 |
| --- | --- | --- | --- | --- |
| assign-in-condition | 语法严重错误 | error | token 恢复路径 | 条件语句中裸 `=` |
| syntax-error | 语法严重错误 | error | SyntaxError 兜底 | 其他无法解析的语法错误 |
| unbalanced-bracket | 语法严重错误 | error | 字符扫描恢复路径 | `(`/`[`/`{` 或 f-string `{` 未闭合 |
| undefined-variable | 逻辑 | error | 作用域链解析 | 引用未绑定变量且非 builtins |
| unused-variable | 规范 | warning | 绑定-使用分析 | 函数局部变量声明后从未引用 |
| bare-except | 规范 | warning | AST：ExceptHandler.type is None | 裸 `except:` |
| prefer-orjson | 性能 | warning | AST：Import/Attribute+Call | `import json` / `json.loads` / `json.dumps` |
| unused-import | 规范 | info | Import 节点 + 全树 Load 收集 | 导入名从未被引用 |
| scenario-rule | 特定场景 | warning | 场景配置驱动 | 违反场景命名/结构约定 |

规则输出统一为 Issue 模型：`{行号, 列号, 严重程度, 规则名, 问题描述, 修复建议, 类别, 源码片段}`。每条问题**同时给出修复建议**（如 assign-in-condition 建议 `=` 改 `==`、若需赋值用 `:=` 或拆分语句），满足"问题描述+修复建议"要求。

### 结构化输出（JSON 片段示例）

```json
{
  "tool": "code-reviewer", "version": "1.0.0", "scenario": "general",
  "summary": {"files": 11, "error": 4, "warning": 7, "info": 4, "total": 15},
  "results": [
    {
      "file": "code_review_testcases/test_case_08_unbalanced_bracket.py",
      "parse_success": false,
      "syntax_error": {"message": "f-string: expecting '}'", "line": 8},
      "issues": [
        {
          "line": 8, "column": 20, "rule": "unbalanced-bracket",
          "severity": "error",
          "message": "括号不匹配，缺少闭合的 `}`",
          "suggestion": "补全缺失的闭合括号，或检查是否存在未闭合的 f-string 表达式",
          "source_line": "    message = f\"用户 {name} 年龄 {age\""
        }
      ]
    }
  ]
}
```

三种形式报告均为脚本一次性生成（`reports/full_report/review_summary.{json,markdown,html}`）；HTML 报告为自包含单文件（无外部依赖），带严重程度徽章、按文件分组的彩色视图，可直接打开浏览或截图归档。

## 四、使用 AI 工具（Claude Code）的研发过程记录

本作业全程由 **Claude Code（Claude Opus 5）** 辅助完成：从需求解析、架构设计、编码实现、调试修复到测试与文档。以下按阶段记录**关键提示词（原文）**与产出，以及过程中的**反思与迭代**。

### 阶段 1：需求解析（提示词）

> 这里为作业说明文档：其中描述了需要完成的作业的内容，配套压缩包内为对应的一个测试集，帮我实现作业的具体内容，注意功能完善

- **我的输入**：作业 docx + 测试集 tar.gz；
- **AI 产出**：自动解压测试集、提取 docx 全文，输出需求清单：三类检查能力、8 条基线规则（含 2 个正例+8 反例的评判细节）、error 红线、评分维度；
- **人机分工**：我负责判断"预期结果 JSON 的行号与测试文件实际行号存在 1~2 行偏移（标准答案先于文件生成）"以及"test_case_09 中标准答案漏了 `import math`"这两处测试集自身瑕疵，确认真实行号才是正确行为，工具按实际位置报告并在报告中说明。

### 阶段 2：架构与规则设计（提示词）

> 基于 AST 实现规则检查，不得仅用字符串匹配；规则要配置化；工具应形成完整链路，至少输出结构化报告

- **AI 产出**：给出分层+注册表架构草案、9 条规则拆解、Issue 数据模型、JSON/Markdown/HTML 三种 formatter 与 CLI 参数设计；
- **关键反思**：初版设计把语法错误全部归为 `syntax-error`，我指出 test_case_03/08 会被"通用语法错误"吞掉、且无法区分具体缺陷 → 与 AI 协作演化出"AST 失败恢复路径 + 具体缺陷优先 + 兜底抑制"方案，这正是本工具最有价值的设计点。

### 阶段 3：编码实现（提示词）

> 实现语法严重错误规则（含 AST 失败恢复机制）、实现变量/导入/异常/性能规则、完整 CLI、场景规则与按场景加载设计

- **AI 产出**：13 个源代码文件（引擎/模型/配置/格式化/上传/6 个规则模块）；规则全部基于 AST/作用域分析；
- **人机分工**：我审查了作用域分析中"类作用域不参与方法体解析""推导式第一个 iter 在外层求值""海象赋值绑定到最近函数/模块作用域"等语义细节，要求与 Python 运行时一致，避免将来误报。

### 阶段 4：调试与迭代（关键提示词）

> [运行脚本后] 失败: 'ScenarioConfig' object has no attribute 'get' / [单测 4 个失败]

- **缺陷 1**：场景工厂把 `ScenarioConfig` 对象当 dict 使用 → 改为访问 `.extra_rules`；
- **缺陷 2**：f-string 扫描器在未闭合 `{` 时把字符串末尾引号当内容吞掉（连注释里的 `}` 都拿来配对了）→ 修正为"3.10 词法下引号即终止符，剩余花括号报 unbalanced-bracket"；
- **缺陷 3**：try 块内导入的 `in_try` 计数器接了 visit_Try 但忘了在 `visit_Import` 使用 → 补齐；
- **缺陷 4**：`import numpy as np` 未使用时消息报 `numpy`（应为本地名 `np`）→ 统一报告绑定名；
- **缺陷 5（最重要）**：方法内裸引用类属性未报 undefined-variable —— 作用域解析没有跳过 class 作用域，与运行时语义不符 → 修复并加单测固化；
- **反思**：这轮"55 个测试 → 4 个失败 → 逐个定位"的闭环证明：**把语义边界写进测试才是防回归的关键**，AI 生成的代码必须配工程级验证。

### 阶段 5：验证与报告（提示词）

> 运行测试集验证（error 0 漏报、正例无误报）/ 撰写 README 与实践报告并交付

- **产出**：55 条单元+集成测试全部通过；11 个测试用例与标准答案对比：**漏报 0（含全部 error 级）、多报 1（标准答案遗漏的 `import math`）**；README、本报告、三格式报告与批量脚本交付。

| 场景约定（如评分函数命名） | 新人不知、老人忘查 | 按场景自动叠加，规则可沉淀 |
| 评审耗时 | 每个文件 5~15 分钟 | **< 1 秒/文件**（批量 < 5 秒） |

**质量卡控左移**：工具部署在开发阶段（本地/CI 门禁），error 级问题在提交前拦截——对应作业背景提到的"大模型参数配置不规范、组件版本不匹配等到生产才发现、修复成本高"问题，本工具把修复成本从线上 SLA 级别降为开发期分钟级。

### 6.3 扩展性（加分项）

已实现：规则全部配置化（JSON 启停/分级）、场景规则集化（新增场景=新增 JSON）、三种结构化报告、`--strict` 门禁退出码、stdin 管道接入、云文档上传（webhook/Lark Cli）、单文件异常隔离与滚动日志。后续方向：多语言（Go/Java AST 适配层）、规则去重与跨文件分析（模块级 import 图）、与 CI（流水线调用 + 报告内嵌）与 AI Agent 评审（大模型对 warning 级问题的语义复检）打通。
